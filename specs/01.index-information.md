# 01 — Index page and global shell

Status: accepted (revised 2026-09-06 — see revision history)
Date: 2026-09-06
Requested by: CEO, TournaWin
Depends on: `00-tech-stack.md`

## Goal

Establish the public entry point of TournaWin and the global shell every future screen
inherits: navigation, theming, language, typography, and the motion language.

This requirement is **foundational, not cosmetic**. Every decision here is one that becomes
expensive to reverse once feature screens exist.

## Revision history

| Rev | Change | Driver |
|---|---|---|
| 1 | Initial spec | CEO brief |
| 2 | Matches creatable **without an account**; tournaments capped at **2 free**; menu **fully visible to everyone** | CEO, 2026-09-06 |
| 3 | Tournament cap is **lifetime**; match shape defined (team vs team, manual score, **not live**); **100 free matches**; ownership field is `owner_uuid`; anonymous matches **claimable** | CEO, 2026-09-06 |

## In scope

- Landing ("index") page with a soccer ball → goal hero animation
- Global navigation shell, **fully visible regardless of auth state**
- Access model: what works anonymously, what requires an account
- Design tokens: typography, colour roles, spacing, motion
- Dark mode
- Language switching (EN/ES)
- Responsive layout (assumption 2 of `00-tech-stack.md`)

## Out of scope

- Actual authentication (Login is a route + entry point; the flow is a separate requirement)
- Tournament/match creation logic (menu entries route to placeholders)
- Payment processing — the upgrade path routes to Pricing; no checkout in this requirement

## 1. Typography

Two requirements drive this: **tabular figures** (scores and standings must not jitter as
digits change) and **Latin Extended** coverage (Spanish needs á é í ó ú ñ ü).

| Role | Font | Why |
|---|---|---|
| Display / headings | **Barlow Condensed** | Condensed athletic character; narrow enough for team names in bracket cells |
| Body / UI | **Inter** | Exceptional small-size legibility; true tabular figures via `tnum` |
| Scores / data | Inter with `font-variant-numeric: tabular-nums` | Digits occupy equal width, so numbers do not shift |

Both are free, variable, and cover Latin Extended.

**Alternative if one family is preferred:** the Archivo superfamily (Archivo + Archivo Narrow +
Archivo Expanded) gives display and body from one typeface at the cost of some personality.

### Loading strategy

Self-host via Fontsource (`@fontsource-variable/inter`, `@fontsource/barlow-condensed`) rather
than the Google Fonts CDN:

- no third-party request on every page load (GDPR-relevant, since EU users are plausible)
- fonts are bundled and fingerprinted by Vite, so they cache properly
- no dependency on an external host being reachable

```css
:root {
  --font-display: "Barlow Condensed", system-ui, sans-serif;
  --font-body: "Inter", system-ui, sans-serif;
}
```

## 2. Colour

The brand palette is adopted as given. What follows is **how it must be bound to roles**,
which is a separate decision from which colours exist.

### Measured contrast (WCAG 2.1, against white)

| Shade | Hex | Ratio | Usable as text / with white text? |
|---|---|--:|---|
| 50–300 | `#e7ffe4`–`#5bff50` | 1.06–1.32 | No |
| 400 | `#29fe1d` | 1.37 | No |
| 500 | `#08e500` | 1.72 | No |
| 600 | `#03b800` | 2.67 | No |
| 700 | `#008e00` | 4.31 | Large text only (≥18.66px bold / 24px) |
| **800** | `#076d08` | **6.56** | **Yes — AA** |
| **900** | `#0b5c0d` | **8.23** | **Yes — AA** |
| **950** | `#003403` | **14.07** | **Yes — AAA** |

**Consequence:** the conventional `bg-primary-500 text-white` button pattern fails badly here
(1.72:1 against a 4.5:1 requirement). It must not be used.

The bright shades are not wasted — against **near-black** text they are excellent
(`#29fe1d` = 15.29:1, `#08e500` = 12.22:1). They are accent and dark-mode colours, not
light-mode text colours.

### Semantic token bindings

```css
/* Light */
:root {
  --primary:            #076d08;  /* 800 — white text: 6.56:1 */
  --primary-foreground: #ffffff;
  --accent:             #29fe1d;  /* 400 — near-black text: 15.29:1 */
  --accent-foreground:  #0a0a0a;
  --brand-text:         #0b5c0d;  /* 900 on white: 8.23:1 */
}

/* Dark — same palette, inverted bindings */
:root.dark {
  --primary:            #29fe1d;  /* 400 becomes primary on dark ground */
  --primary-foreground: #0a0a0a;
  --accent:             #5bff50;  /* 300 */
  --accent-foreground:  #0a0a0a;
  --brand-text:         #99ff90;  /* 200 */
}
```

### Two gaps the brief does not cover

1. **Neutrals.** A UI cannot be built from one hue. Text, borders, surfaces, and disabled
   states need a neutral ramp. Proposed: Tailwind `zinc` (slightly warm, sits well with green).
2. **Status colours.** Error (red), warning (amber), and info (blue) are required and are not
   in the brand palette. Note the collision: *success* is conventionally green, which is also
   the brand colour — so a "saved" toast and a brand button look alike. For **W/D/L** chips in
   standings, distinguish by shape and label rather than hue alone, which is also the
   colour-blind-safe choice.

## 3. Motion

### Recommendation: **Motion** (formerly Framer Motion), one library

A ball arcing into a goal is a keyframed 2D transform over an SVG — comfortably within
Motion's range, and Motion is needed anyway for route transitions, menu drawers, and list
animations. Adding a second animation library for one hero piece is not justified.

| Considered | Verdict |
|---|---|
| **Motion** | ✅ React-native, declarative, springs, layout animations. Covers the hero *and* general UI |
| GSAP | Extremely capable timelines and now fully free, but a second paradigm alongside React for one set piece |
| Rive | **Best option if a designer joins** — interactive state machines could react to real events ("goal scored"). Requires a designer and a `.riv` asset |
| Lottie | Playback only; needs a designer to produce the animation |
| React Three Fiber | Real 3D. Disproportionate weight and complexity for a hero animation |
| Plain CSS | Sufficient for a bounce; insufficient for arc + net ripple + celebration choreography |

### Non-negotiable: reduced motion

```tsx
const shouldReduceMotion = useReducedMotion();
```

Users with `prefers-reduced-motion: reduce` get the end state without the traversal. This is an
accessibility requirement, not a preference: vestibular disorders make large motion physically
unpleasant.

## 4. Access model

### What a match is

Confirmed by the CEO: a match is **one team versus another team, with a score entered manually
by the user**. There is no live timing, no play-by-play, no real-time feed.

This matters beyond the domain model — it **confirms** the `00-tech-stack.md` decision to leave
WebSockets out. Scores change when a human types them, so TanStack Query's refetching is
sufficient. No push transport is needed.

### Capability tiers

The platform has **three tiers of capability**, and the boundary between them is the most
consequential thing in this revision.

| Capability | Account required? | Free limit |
|---|---|---|
| Browse, view a match or tournament | No | Unlimited |
| **Create a match** | **No** | **100 matches free** (see tension below) |
| **Create a tournament** | **Yes** | **2 tournaments, lifetime** |
| Tournament 3 and beyond | Yes + paid plan | — |

### Anonymous match ownership

An anonymous creator has no identity, so ownership is expressed as a **capability URL**: the
match carries an unguessable token, and holding the link *is* the credential.

```
/m/{match_id}?k={capability_token}     # can edit
/m/{match_id}                          # can view
```

Consequences that must be designed for, not discovered later:

- **The token is a secret.** It must be high-entropy (≥128 bits), never logged, and never
  placed in a page the search engines can reach.
- **Loss is unrecoverable.** With no account there is no "email me my link". The UI must warn
  the creator to save the link, and offer to email it as a convenience.
- **Claiming — confirmed.** If the creator later registers they can attach anonymous matches
  they still hold links for. The ownership column is **`owner_uuid`**, nullable on matches, set
  on claim.
- **Retention.** Anonymous matches accumulate with nobody accountable for them. **Deferred** —
  a data-retention commitment to settle with the match requirement, not here.
- **Abuse.** Anonymous writes are an open door. Rate limiting by IP is **mandatory**, not
  optional. This is a natural fit for API Gateway throttling via Floci (`02-floci-local-aws.md`).

### Tournament quota — lifetime

**Confirmed: 2 tournaments ever, not 2 at a time.** Deleting or finishing a tournament does
**not** free a slot; the third tournament a user ever creates requires a paid plan.

Consequences to carry into the domain model:

- The count is over **all tournaments ever created** by a user, so deleted tournaments must
  still be counted — a hard delete would hand back a free slot. Deletion must be **soft**
  (`deleted_at`), or the lifetime count kept as its own counter.
- This is commercially much stronger than a concurrent cap, and much harsher on casual users.
  Expect it to be the single biggest driver of signup abandonment; worth measuring.

Tournaments require an account because **a quota cannot be counted without an identity**.

- The limit is **enforced server-side**. Hiding the button at the limit is an affordance; the
  API must reject the request regardless of what the client renders.
- The frontend shows remaining quota ("1 of 2 free tournaments used") — quota state comes from
  the API, never computed client-side.
- Hitting the limit routes to **Pricing** with context, not a bare error.

### Unresolved tension: 100 free matches vs. anonymous creation

Two confirmed decisions pull against each other:

- matches can be created **with no account**, and
- matches are capped at **100 free**.

A quota needs an identity to count against, and an anonymous creator has none. Counting by IP
punishes shared networks and is trivially evaded; counting by browser session is erased by
clearing storage. The plausible resolutions — anonymous creation stays unlimited but
rate-limited, or matches beyond some threshold require an account — are **a product decision,
not a technical one**.

**Deferred by the CEO**: not needed for the index page. Flagged here so it is not discovered
during implementation of the match requirement.

### Effect on `00-tech-stack.md`

Assumption 1 says *"single deployment, not multi-tenant SaaS."* A free-tier cap does **not**
overturn it: the quota attaches to a **user**, not to an organisation. No tenant scoping, no
member roles, no org-scoped tables.

What it *does* overturn is the revision-1 decision that Pricing is purely marketing. **A free
tier implies a paid tier.** Billing is still out of scope here, but it is now a committed
direction rather than a hypothetical, and should get its own ADR before the domain model grows.

## 5. Navigation

**Every menu item is visible to every visitor, logged in or not.** This reverses revision 1,
which hid authenticated actions.

The rationale is sound: hidden capability is undiscovered capability. Showing "Create a
tournament" to a logged-out visitor advertises the product. But it only works if the click
*captures intent* rather than dead-ending.

| Item | Visible | Logged out behaviour |
|---|---|---|
| Create a match | Always | **Works fully.** No prompt, no account |
| Create a tournament | Always | Login prompt → **resume creation after auth** |
| Pricing | Always | Public page |
| Log in / Account | Always | Swaps label by auth state |
| Dark mode | Always | Works |
| Language EN/ES | Always | Works |

### Deferred action

The pattern that makes a fully visible menu honest:

1. Visitor clicks "Create a tournament"
2. Intended destination is stored (`?next=/tournaments/new`)
3. Login or registration
4. **Redirected to the original action, not to a generic home page**

Losing step 4 is the most common implementation of this pattern and the reason users abandon.

The `next` parameter must be validated as a **relative path only** — accepting an absolute URL
creates an open-redirect vulnerability, which is a standard phishing vector.

### Structure

```
┌───────────────────────────────────────────────────────────────┐
│ TournaWin   Create match   Create tournament   Pricing        │
│                                        ☾   EN/ES   [Log in]   │
└───────────────────────────────────────────────────────────────┘
              └────── always visible to everyone ──────┘
```

Below `md` (768px) the links collapse into a drawer; theme and language stay in the header, as
they are the controls a user is most likely to want immediately.

**"Create a match" is the primary call to action** on the landing page. "No account needed" is
the strongest conversion message the product has, and it should be stated on the button itself.

## 6. Internationalisation (EN/ES)

**Library:** `react-i18next`.

**Boundary:** the frontend owns all translation. The backend returns **error codes**
(`TOURNAMENT_ALREADY_STARTED`), never user-facing prose. A translated string in an API response
would make the API's contract depend on the caller's locale.

**Scope:** UI chrome only. User-generated content (tournament names, team names) is stored and
displayed as entered — never machine-translated.

**Detection order:** stored preference → `navigator.language` → `en`.

**Locale-aware formatting:** dates and numbers go through `Intl`, never manual formatting.
Spanish uses `dd/mm/yyyy` and `.` as thousands separator; hardcoded formats break it.

---

## 7. Theme

- `class` strategy: `.dark` toggled on `<html>`
- Default: follow `prefers-color-scheme`; an explicit choice is stored and wins thereafter
- Applied via an inline script **before first paint** to avoid a flash of the wrong theme
- Three states: `light`, `dark`, `system`

---

## 8. Responsive

Mobile-first. Breakpoints per Tailwind defaults (`sm` 640, `md` 768, `lg` 1024, `xl` 1280).

The hero animation must degrade gracefully: on narrow viewports the goal is cropped rather than
scaled to illegibility. Playwright covers both a desktop and a mobile project.

## 9. Acceptance criteria

```gherkin
Feature: Global shell

  Scenario: Language switching
    Given I am on the index page in English
    When I select "ES" from the language switcher
    Then all interface text is displayed in Spanish
    And my choice persists after a page reload

  Scenario: Dark mode follows the system by default
    Given I have never chosen a theme
    And my operating system is set to dark mode
    When I open the index page
    Then the dark theme is applied without a flash of light theme

  Scenario: Explicit theme choice overrides the system
    Given my operating system is set to dark mode
    When I select the light theme
    Then the light theme is applied
    And it persists after a page reload

  Scenario: The full menu is visible to anonymous visitors
    Given I am not logged in
    When I open the index page
    Then I see "Create a match", "Create a tournament", "Pricing" and "Log in"

  Scenario: Creating a match needs no account
    Given I am not logged in
    When I choose "Create a match"
    Then I am taken to match creation
    And I am not asked to log in

  Scenario: Creating a tournament defers to login and resumes
    Given I am not logged in
    When I choose "Create a tournament"
    Then I am asked to log in
    And after logging in I am taken to tournament creation
    And I am not returned to the home page

  Scenario: The next parameter cannot be used as an open redirect
    Given a login link carrying an absolute URL as its next parameter
    When I complete login
    Then I am redirected to a relative path within the application
    And never to the external URL

  Scenario: Free tournament quota is enforced by the server
    Given I am logged in and already own 2 free tournaments
    When I request creation of a third tournament directly from the API
    Then the request is rejected
    And the rejection names the plan limit as the reason

  Scenario: Reaching the quota routes to Pricing with context
    Given I am logged in and already own 2 free tournaments
    When I choose "Create a tournament"
    Then I am shown the plan limit and offered the Pricing page

  Scenario: An anonymous match is reachable only with its capability token
    Given a match created without an account
    When I open its URL without the capability token
    Then I can view the match
    And I cannot edit it

  Scenario: Hero animation respects reduced motion
    Given my system requests reduced motion
    When I open the index page
    Then the ball and goal are shown in their final position
    And no traversal animation plays

  Scenario: Mobile navigation
    Given I am on a 375px-wide viewport
    When I open the index page
    Then navigation links are collapsed into a menu drawer
    And the theme and language controls remain directly accessible

  Scenario: Contrast compliance
    Given any text rendered against a brand-coloured background
    Then its contrast ratio is at least 4.5:1
```

   while Login is only a route with no flow behind it.

mode, EN/ES switching, the responsive shell, the fully visible menu, and the hero animation.
